从 SDV 到 AI-DV：车载软件架构的演进思考
Architecture Note · 2026.11
从软件定义
到 AI 定义
车载软件架构正在经历第三次范式迁移。SDV 解决的是功能如何被软件定义与迭代；AI-DV 要解决的是车辆如何理解场景、组织能力、并对结果负责。
两者之间隔着的并非模型能力，缺的是一层从未存在过的东西：让 AI 能够安全调用车辆能力的语义层。

架构主线SOA → Capability → Agent
业务分层L1 → L4

安全前提AI 不触执行链路
01 / 05
范式的分界不在技术栈，在谁决定这辆车能做什么
行业叙事常把三个阶段说成技术升级。真正的差别在责任主体：硬件时代由配置表决定，软件时代由功能清单决定，AI 时代由目标与场景在现场决定。

Judgment
三个阶段不是替代关系。AI-DV 不会取代 SDV，它站在 SDV 之上：没有稳定的服务层，Agent 没有可靠的操作对象；没有确定性执行链路，AI 的判断无法落地。
把这三者当成三选一，是这类讨论里最常见的误读。真正的工程问题是在哪一层插入语义能力，以及如何保证插入之后执行链路仍然可论证。
一张表看清差异 DIMENSION
功能怎么来 固化 → 预定义可升级 → 场景触发、运行时生成
用户怎么用 操作开关 → 发指令 → 表达意图
系统怎么协同 硬线连接 → 固定服务调用 → 能力动态编排
场景怎么覆盖 配置表枚举 → 场景包预设 → 运行时理解
组织形态 按零部件 → 按功能域 → 按平台与场景
最后一行最容易被低估。前四行讲技术，组织形态才是转型真正卡住的地方：功能的边界可以画在功能域里，能力的边界画不进去。
02 / 05
把车控业务拆成四层，关键是说清每层对什么负责
四层划分的价值不在分层本身，而在它强制回答一个问题：能力编排出错时，责任落在哪一层。这条线决定了 Agent 能碰什么、不能碰什么。

为什么 L3 必须掌握
判断依据是安全责任的落点，与技术能力强弱无关。能力编排一旦出错，后果落在车辆执行上，责任主体必然是掌握执行链路的一方。
把编排权交给外部平台，等于把安全责任留在车内、把编排权交到车外。这个结构在事故追溯时站不住，也无法向功能安全论证交代。
所以 L3 该拿，但拿的必须是编排与治理，不能让 Agent 去碰执行。这条界线的工程含义很具体：Agent 的输出是意图与任务，不是控制量。

按这条线评估，多数平台处在经典向场景化过渡的位置：接口基本齐了，场景仍靠开发人员写代码落地。这是第一个要补的洞，也是后两代能否成立的前提。
04 / 05
接口的形态决定 AI 能不能用得上
这是整条演进路径上最具体、也最容易被跳过的一环。接口不改，Agent 只能退化成一个更大的场景包。
BEFORE · INSTRUCTION
调用方必须知道怎么做
SetACMode(mode)
SetTemperature(value)
SetFanSpeed(level)
SetAirDirection(dir)
四个孤立动词，谁调用谁负责组合
AI 需要先学会空调的全部参数语义
后果：每加一个场景，就要改一次代码
AFTER · CAPABILITY
调用方只表达想要什么
Capability: CabinComfort
一个能力，不是四个动词
INPUTS
target_comfort · occupant_context · environment
CONSTRAINTS
温度范围 · 能耗上限 · 除霜优先级 · 安全条件
EXECUTION
能力规划 → 空调控制 → 座椅协同
OUTPUTS
execution_status · actual_state · comfort_feedback
语义描述：这个能力做什么、什么时候可用
约束条件：什么状态下不允许调用（AI 必须能读到）
执行细节对上完全隐藏 → AI 无需理解电机与 PWM 信号
输出带反馈 → Agent 可判断是否需要调整策略
CORE ASSETS SHIFT
API 数量
Capability · Semantic · Context · Constraint · Execution · Feedback
FIG 04
接口从「四个动词」到「一个带约束的能力」的解剖。真正新增的是约束声明与执行反馈这两块，它们此前不属于接口的一部分。
指令接口的隐含假设
调用方必须知道被调方的内部结构。这个假设在人写代码时成立，在模型自主调用时不成立：模型无法可靠地推断「温度调多少合适」这类语义边界。
能力接口的显式契约
调用方只需表达目标。约束由能力自己声明，执行过程内部完成，结果带回反馈。模型需要理解的东西被压缩到「这个能力做什么、什么时候不能用」。
这件事与正在推进的原子服务设计、架构模型建模是同一件事的两面。区别只在服务对象：原子服务的对象是软件工程师，能力目录的对象还要加上 Agent。因此能力目录必须多两层信息：语义描述（AI 能读懂这个能力做什么）与约束条件（AI 知道什么时候不能调）。这两层目前都不存在，是语义层要补的核心内容。

三条不可违反的原则 CONSTRAINT
Agent 与实时控制解耦
Agent 负责理解、规划、协调，不接管 MCU 上的实时控制算法。Agent 的输出是任务与意图，该任务必须穿过能力接口、策略校验、安全仲裁三道才落到执行。
SOA 与 Agent 互为前提
没有 SOA，Agent 没有可靠的操作对象；没有 Agent，SOA 仍要人预先编排每个场景。两者是配套关系，任何一方单独推进都做不成。
安全体系独立于 AI 推理链路
制动、转向、动力、悬架几个安全关键域，AI 可以参与上层目标规划，不能绕过经过安全论证的执行链路、控制器和安全机制。

Agent 的落地边界：链路六步，第五步决定成败
前四步现在业界都能做出演示，第五步决定这套东西能不能上车。策略校验远不止加一道判断，它要求每个能力把约束条件显式声明出来，且校验逻辑本身经过论证。

AI 助手与 AI Agent 的差别不在模型大小，在是否拥有目标、上下文、工具调用与任务验证的完整闭环。聊天不是价值，完成任务才是。

推进顺序建议
五个形态里，测试 Agent 与研发 Agent 边界最清楚，目标、工具、输入输出、结果验证四条都明确，应当先做。车控 Agent 排在后面，它的瓶颈不在模型，在能力目录：没有语义接口，Agent 无米可炊。
也就是说，能力层是这一切的前置条件。跳过能力层直接做 Agent，得到的是一个演示，不是一个产品。
附 / 结论
三条主线的收敛点
把九个章节压成一句话：三条演进主线最终都指向同一个东西，一层此前不存在的语义能力层。
PRODUCT
功能驱动 → 场景驱动 → 意图驱动
ARCHITECTURE
SOA → Capability SOA → Agent 架构
ENGINEERING
软件工程 → AI 辅助工程 → AI 原生工程
语义能力层
能力目录 · 语义接口 · 约束声明 · 执行反馈
三条主线的时间尺度不同，但收敛点是同一个。这也是为什么它值得先投入：一个前置条件同时服务三个方向。
FIG 08
产品、架构、研发三条演进主线收敛于语义能力层。它是三条线的共同前置条件，而不是其中某一条的子项目。
关于边界的一句话：这套演进里，AI 的位置是智能协调者，逐步成为受约束的策略决策者，不会成为底层实时控制器。守住这条，架构可以放开手演进；守不住，演进方向会在某个节点上被迫回退。
