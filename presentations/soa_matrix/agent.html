01战略命题

让车辆完成目标，
让用户少做协调

车控 Agent 的价值、建设条件与演进路径

面向业务价值受约束的目标组合复用现有 SOA
战略与实施建议2026.11 · REV 1.0
本报告回答五个问题：有什么新增价值，为什么需要共同车控职责，何时值得 Agent 化，怎样落地，怎样证明投入有效。所有阶段、资源和收益均为建议或待验证假设，不是已批准项目。
02管理摘要

先确定业务增量，再选择 Agent 的形态

建议以一个完整业务切片验证价值，而非先建设全量平台。

01

价值

满足未预定义的合理需求，减少用户逐项操作，形成可复用的个人场景。

02

条件

共同协调职责已经有需求；独立 VCC、智能规划和大模型仍需分别论证。

03

路径

现有能力闭环 → 边界内组合 → 个人复用 → 产品化；按证据逐步投入。

建议决策：认可方向，指定试点责任团队；以技术与业务证据决定后续扩展。
不要把跨入口协调缺口直接等同于大模型的必要性。先建立任务责任与执行闭环，再对动态规划与确定性基线进行比较。
03战略对齐

SDV 是产品范式，SOA 是重要架构基础

沿用战略材料的大方向，以能力与结果契约连接智能规划和既有执行。

产品演进软件可迭代 → 理解目标、组织能力发展方向；不承诺特定年份
业务协调座舱理解需求 · VCC 协调车控目标职责边界先于技术选型
能力契约语义 · 条件 · 约束 · 状态 · 结果按真实能力逐步补齐
执行基础SOA 服务 · 系统产品 · 中间件与底软稳定执行、域内策略与保护

SOA 是本项目的核心积累；逻辑分层不等于新增部署层，也不要求重写全部服务。

战略参考提出 SOA、能力、Agent 的演进方向。我们的方案保留其方向，明确 SDV 不等同于 SOA，能力语义也不一定需要独立进程实现。
04业务价值

新增价值：满足“没有现成功能入口”的需求

单纯更准确地识别语音、调用固定模式，不能独自证明建设车控 Agent 的价值。

01

覆盖更多需求

在已有能力内组合出未被逐个预设的场景；不凭空增加硬件功能。

02

减少用户操心

用户表达效果与限制，由车辆选择、协调并根据结果调整，而非反复试设置。

03

越用越适合个人

保存个人目标、约束和使用反馈，按当前条件复用，而非仅记住几个参数。

车企价值：复用既有能力覆盖更多需求，并以真实使用证据指导场景产品化。
这些价值属于智能车控整体，不天然要求独立车控 Agent。座舱也可承接部分职责。后续页面论证为什么共同车控职责与动态规划有时值得独立组织。付费、销量和品牌收益仍是商业假设。
05价值验证

用同一批任务比较，证明投入是否值得

对比现有固定场景、扩展规则方案、目标规划方案；不只比较正常路径演示。

价值问题观察指标避免误判
是否覆盖新增需求范围内需求的成功／部分完成／拒绝／失败／未知分布单独报告范围外请求；不能靠拒绝抬高成功率
是否减少用户成本操作次数、澄清与纠正次数、任务起效与完成时间更智能不能以不可接受的等待为代价
是否降低工程成本新场景接入工时、重复逻辑、验证与维护投入一并计入能力建模和异常处理成本
是否形成长期复用个人场景再次使用情况、跨入口／车型复用情况区分尝试、成功使用与实际偏好
先建立基线和测量口径，再由业务负责人确定目标值；本报告不虚构收益百分比。
建议采用同样的能力、车辆条件与任务集评估三种方案。收益归因应排除单纯语音理解改进和新增硬件的影响。
06必要性决策

协调缺口，不自动等于 Agent 必要性

将四个决策分开，避免“先定组织和技术，再寻找需求”。

决策成立依据可选承载
统一车控协调职责跨入口／跨系统冲突、任务状态和整体结果缺口扩展既有协调机制或定义共同职责
独立 VCC 边界整体任务责任、跨入口复用、独立演进价值逻辑模块可先独立；部署不必立即独立
引入 Agent 规划运行时选择路径、动态组合与重规划有实际收益规则＋规划混合，与确定性基线比较
使用大模型语义解释或候选生成收益超过时延与验证成本仅用于适合的环节，不进入实时控制
VCC 是职责对象，Agent 是实现能力，LLM 是可选技术，不应合并为一次决策。扩展现有系统能够解决的问题应优先复用。
07职责边界

用户意图可以来自不同入口，车辆目标需要一致承接

按责任分工；既有系统的控制权和保护不因引入 Agent 自动迁移。

01

座舱／手机等入口

表达对象、需求、约束与授权；座舱负责对话和歧义澄清。

02

VCC 车控协调

判断可行性、选择场景、组织目标、协调任务并解释整体结果。

03

系统产品

承诺本域能力，选择执行策略，完成域内控制、仲裁和保护。

外部可提出方案；VCC 对其接受的任务负责。智驾运动控制权限仍由对应体系管理。
共同协调职责放在哪里须结合已有系统评估。图示是建议责任结构，不表示新建部门或指定部署。VCC 不自动成为导航、内容或所有业务的总管。
08能力基础

把接口事实转成可兑现的能力承诺

先做选定能力，再逐步扩展目录；能力不是每个 RPC 外面增加一个名称。

必须明确对应问题责任参与
语义与边界能做什么、针对谁、“稍暖”是什么意思FO＋SO
条件与适用性车型、配置、版本、设备和当前状态是否支持SO＋AI＋领域架构师
输入与约束精确目标、偏好、硬限制、控制来源VCC 与使用方／产品 FO
执行与结果如何映射服务、何时算完成、依据是什么领域架构师＋SWE＋验证
演进与维护变更影响谁、谁维护、怎样回归产品责任团队＋矩阵支持
AiCabinFuncMgr 等已有接口含场景、区域、相对调温等语义，应优先研究复用。IDL 表达存在不证明全部车型已经实现完整能力。
09整体方案

VCC 管目标与任务，系统产品管本域执行

在现有服务之上补契约与适配，按缺口建设，不先重构全部系统。

输入精确命令／预定义场景／结构化目标组合身份、对象与授权
VCC匹配与规划 → 可行性 → Mission 协调整体状态、冲突与退出
能力边界目标与结果契约 · 必要的系统侧适配本域条件与执行策略
SOA 基础服务调用／事件／状态／错误及质量信息沿用真实底座语义
执行闭环系统产品与控制器执行，持续保护反馈事实与结果证据
能力适配不必都是独立组件。soa_adaptor 是通信及 IDL 桥接积累，不承担规划和业务仲裁。具体软件职责与部署需与独立软件架构矩阵共同确认。
10对外交互

固定表达规则，容纳新的目标组合

同一业务语义适配不同入口；精确请求可保持确定性路径。

{
  "request_id": "rest-001",
  "goals": ["R2R_WARMER", "R2R_DIMMER"],
  "constraints": {
    "seat_movement": "FORBIDDEN",
    "front_settings": "PRESERVE"
  },
  "preference": "QUIETER"
}

实际契约需补齐

  • 目标类型、区域和相对变化含义
  • 来源授权、当前可用性和版本
  • 接受／澄清／拒绝，以及后续结果
  • 修改、取消与状态订阅

JSON 仅为表达示意；身份权限由可信接入确认。MCP／A2A／现有服务均未冻结选型。

示例中的枚举是解释性缩写，正式设计应采用有类型的目标参数。未定义的新能力仍需扩展语义与实现，任意 JSON 不等于任意功能。
11关键工程条件

能发出请求，还要能证明发生了什么

执行结果和状态质量，是自主规划能够成立的基础。

01

结果要分层

接受 ≠ 已发送 ≠ 域内执行成功 ≠ 整体目标满足；无法确认时明确未知。

02

数据要有来源

SM buffer 读取成功不等于新帧；读取时间不能替代源端时间，E2E 不伪造。

03

约束要持续有效

受理与执行检查相衔接；运行中条件变化、手动介入和故障由各层按职责处理。

底座需求按业务推导：关联、时效、错误、队列和资源预算；不统一强制一种 QoS。
本报告不提供功能安全符合性结论。关键点是模型外独立执行约束、保持现有保护、区分不同通信与业务状态。取消不等于物理撤销，恢复需单独定义。
12演进策略

由闭环到组合，由使用证据到产品化

按能力成熟度推进；不同能力可以处于不同阶段。

STAGE 01

场景闭环

少量高频预定义／参数化场景，补齐能力和结果。

推进条件
正常、异常、拒绝和未知均有可解释反馈
STAGE 02

受约束组合

在已验证能力与组合规则内进行路径选择。

推进条件
相对规则基线有收益；冲突和运行变化可控
STAGE 03

个人场景复用

保存目标、约束与适用条件，支持修改与失效。

推进条件
再次运行能校验当前能力和车辆条件
STAGE 04

反馈产品化

伴生归纳高价值需求，进入正式功能规划。

推进条件
有重复使用证据、责任团队及验证承接
不是全量目录先完成才能试点，也不是所有新场景免代码上线。新增能力、硬件、权限或验收语义仍需产品和工程建设。
13实施步骤

用一个业务切片贯通价值、技术与工程

先验证最关键的假设，再决定组件化与规模化。

步骤必须拿到的结果推进依据
01 选任务与基线清楚的用户问题、范围、替代方案和指标业务价值可观察
02 盘能力与缺口已有能力、限制、映射和责任人避免重复开发或虚构能力
03 定契约与分工任务、目标、结果、冲突和退出语义相关责任方理解一致
04 验关键假设Mock／主机／必要的真实 SDK 与台架证据区分逻辑验证与实车证明
05 业务试点授权条件下验证正常、异常及用户操作收益超过新增成本
06 复盘再扩展保留、调整或停止的证据共性机制有真实复用需求
这些步骤是建议工作分解，不是已确认排期。试点开始前需明确业务 owner、实现团队、验证环境和投入。主机测试不能替代真实 SDK、ECU 和任务效果验证。
14所需能力

业务、产品、平台和验证共同承接

矩阵 COE 提供共性支撑，不能代替业务与工程长期责任。

能力主要承接矩阵贡献
场景与 MissionVCC FO／SO、业务 SWE契约方法与跨团队边界研究
本域目标执行系统 FO／SO、领域架构师、SWE能力映射与服务提升模式
模型与规划VCC 相应算法／软件团队，按实际需要参与适用边界与评估方法
中间件与底座平台架构及底软团队业务需求归纳、机制评估
软件职责与部署独立软件架构矩阵及工程团队提供服务与能力侧约束
验证与反馈业务和相关验证责任团队共用用例、Mock 和证据方法
AI 指车型架构角色，其参与车型分配与适用性评估。本页的模型团队指按需参与的算法和软件专业，不与 AI 角色混淆。
15完整案例 · 1/3

先明确需求，再决定能否承接

二排孩子休息：稍暖、灯光稍暗，不动座椅，不改变前排设置。

MISSION · REST-001

舒服一点，
也别打扰别人。

目标与约束

热舒适与灯光改善是目标；座椅不移动、前排设置保持是硬约束；安静是偏好。

事实与适用条件

确认作用区域、占座及设备可用性；判断共享资源是否允许满足要求。未知信息不能当作已满足。

例子假定目标能力已经定义，并非证明当前车辆已具备。入口澄清对象和授权，VCC 检查能力。若共享资源不能满足硬约束，应拒绝相关目标或请求选择替代，不静默改变前排。
16完整案例 · 2/3

按目标分解，复用系统完整功能

VCC 不维护每个车型的风机、风道与加热设备脚本。

受理

检查来源、对象、约束、当前任务与可用性。

→
任务建立

形成热舒适和灯光子目标，记录整体完成条件。

→
域内承接

热舒适、灯光产品分别评估并执行；不调用座椅移动。

→
结果聚合

汇总子目标与证据；明确达成、运行中或部分完成。

若已有完整休息场景满足约束则复用；有差异时参数化或局部组合，避免每次从零规划。
相对变化的完成标准需由产品定义，不能只看命令写成功。热舒适产品可内部选择其获授权的设备策略，但不能突破本任务硬约束。
17完整案例 · 3/3

条件变化时，怎样继续负责

任务开始之后的行为，决定它是一次联动演示，还是完整任务。

运行事件应有行为向使用方解释
热舒适能力拒绝，灯光可用按预定部分执行政策处理；需要时澄清不能完整满足，说明受限目标及原因
源状态无法确认时效依能力策略处理，保留未知，不伪造完成结果暂不能确认
用户手动调整或退出依控制权规则调整／结束对应目标任务已调整或结束；不默认全部恢复
新空气质量需求与安静冲突VCC 协调整体目标，产品保持本域保护说明取舍、降级及维持范围
状态只是发生了某个值，并不必然证明由本次请求导致。未来关联机制应区分目标状态满足与请求动作完成。恢复基准必须单独定义，不自动回放相反动作。
18学习与业务闭环

从一次需求，走向可复用的个人场景

保存“为什么这样做、什么条件下有效”，而不只是底层动作日志。

候选场景

目标、对象、上下文、约束和组合理由。

→
一次 Mission

执行证据、失败、用户修改和结束方式。

→
个人复用

带版本和适用条件，再运行时重新校验。

→
产品规划

伴生汇集重复需求，评估为正式预定义场景。

候选 ≠ 已验证；个人场景 ≠ 通用产品。模型不能自行扩展物理能力或控制权限。
收益需要通过重复使用和目标达成数据证明。场景记忆和伴生涉及的数据范围、授权和维护政策需由相关业务进一步定义。
19可行性与风险

已有基础支持研究，尚不足以承诺整车效果

把已知、待验证和需要承接的事项分别管理。

01

已有研究基础

已有平台 IDL、应用使用与 SM 桥接研究，部分服务包含场景、区域和相对调节语义。

02

关键待验证

整体结果证据、跨任务规则、真实 SDK 与 ECU 行为、动态规划相对规则的净收益。

03

推进前提

指定业务和产品责任人、实现与验证投入、试点范围、环境和退出条件。

可行性判断：方向可行；独立职责、Agent 化程度与投入规模，以试点证据决定。
此前桥接主机验证证明的是特定代码与 mock 的行为，不证明车控 Agent 或实车 Mission 已经实现。资源、时间和收益都不作无依据承诺。
20决策建议

批准一次可验证的探索，建立可扩展的基础

把战略认可转成有限范围、有责任、有证据的下一步。

01

确认业务命题

选定一个有新增价值的目标型任务，并明确与现有方案的比较基线。

02

指定承接关系

VCC 牵引，相关系统产品、软件架构、底座和验证团队确认参与。

03

支持 COE 赋能

以共同契约、服务提升和验证方法支撑试点；按结果决定扩展。
