本文汇总截至目前围绕车控 Agent 的讨论，重点记录已经形成的业务判断、职责边界、对外能力表达、对内编排方式、场景演进机制与多 Agent 分工，并附上相关例子。

## 1. 核心共识

**开放受约束的目标组合能力，复用系统产品的执行能力，让 VCC 对其承接的 Mission 形成完整责任。**

展开来看，已经讨论清楚的方向有以下几项：

1. 车控 Agent 的价值，是将用户或其他系统提出的车控需求，转化为车辆能够承接、执行并判断结果的任务。
1. 能力开放既要支持精确指令和预定义场景，也要支持在已有能力范围内动态组合的新场景。
1. 动态场景不需要逐个预设编号。需要预先定义的是可组合的目标能力、参数语义、约束与结果，而不是穷举所有组合。
1. VCC 承担车辆控制相关的跨系统目标协调、场景编排、任务仲裁和整体结果判定；系统产品继续承担本域策略和执行闭环。
1. 座舱 Agent 更懂用户，智驾 Agent 更懂车外态势，车控 Agent 更懂车辆如何响应。三者以需求、上下文、目标和结果协作。
1. 预定义场景与动态生成场景可以走向同一个 Mission 执行与反馈框架。预定义场景提供经过产品化的模板，动态组合提供边界内的扩展能力。
1. 用户场景可以持续沉淀，并通过伴生形成后续产品规划的输入；一次生成或一次成功不等于已经成为通用产品能力。
1. 现有 SOA 是重要的执行基础。能否成为面向 Agent 的能力，要同时看业务语义、可用条件、控制权和执行结果，不能只看有没有 RPC。

用一句完整的业务表述概括：

**VCC 在既有能力、组合规则和适用条件内，复用或动态构建满足用户目标的场景；对承接的 Mission 负责，通过执行反馈与用户使用持续沉淀个人场景，并推动高价值场景产品化。**

## 2. 讨论起点与研究范围

### 2.1 已有基础

车控系统已经进行了服务化设计，部分基础能力和场景能力通过服务接口暴露。soa_adaptor 项目的调研又进一步揭示了应用实际使用的接口、字段、通信行为以及状态反馈特点。

因此，当前研究的起点是：已有 SOA 能力能否进一步成为车控 Agent 可理解、可调用、可组合、可判断结果的能力基础。

这里需要分开两件事：服务接口提供调用通路；业务能力定义提供该通路能够完成什么、在什么条件下可以完成、如何证明完成。

### 2.2 消费方不限于座舱语音

车控 Agent 的使用方包括：

- 座舱智能语音助手、NLP 大模型和座舱 Agent。
- 智能驾驶 Agent、世界模型或其他车外态势感知系统。
- 手机 App、远程控制设备，以及未来可能出现的手机侧 Agent。
- 传统 GUI、固定控制面板、确定性自动化逻辑。

因此，对外能力应以稳定的业务语义为中心，同时兼容确定性请求和目标型请求。不能把整个接口设计绑定在某一种自然语言模型、某个座舱入口或某种智能体协议上。

### 2.3 当前没有决定的内容

目前没有冻结最终部署位置、技术栈、协议、完整 IDL、算法实现、车型上线范围和开发排期。本文重点回答业务定位与架构可行性，不把讨论直接转换为实施计划。

几个容易混淆的区别：

- 同一个场景模板可以产生很多次 Mission；每次任务的参与者、车辆状态和结果不同。
- 一个场景可以由多个 Goal 组成，但不一定跨很多服务；是否归属 VCC，主要看是否需要统一任务责任和协调。
- 一个服务不必恰好对应一个 Skill。一个完整能力可能需要调用多个服务，并结合状态反馈才能闭环；一个服务也可能包含多个不同业务能力。
- Agent 是职责形态，不意味着每次调用都必须经过大模型。精确控制和已知场景可以采用确定性路径。

## 4. VCC 的目标与边界

### 4.1 VCC 应负责的事项

VCC 面向车辆控制需求，负责判断当前车辆能做什么、应该怎样协调、是否可以接受，以及最终完成了什么。

具体包括：

1. 识别请求对应的车控目标，结合车辆状态补全执行所需的领域含义。
1. 选择适用的预定义场景，或在既有能力边界内构建目标组合。
1. 明确作用对象、控制范围、硬约束、软偏好、持续时间与退出条件。
1. 判断当前车型、配置、设备状态、运行模式和控制权限是否支持这些目标。
1. 协调相关系统产品的目标、资源、时序和任务冲突。
1. 管理承接任务的执行、修改、中断、取消、降级和结束。
1. 汇总子目标反馈，给出整体完成情况与解释。

这些责任对应的是“任务是否完成”，不能止于“接口已经发出”。

### 4.2 系统产品继续负责的事项

系统产品保留本域功能的实现责任，包括：

- 如何把目标转化为本域控制策略。
- 域内执行时序、状态机与闭环控制。
- 本域请求源仲裁、执行条件和资源处理。
- 实时控制、执行机构保护、安全互锁、故障诊断和本域降级。
- 提供可信的本域状态和结果。

例如，VCC 可以提出“二排右侧改善热舒适、避免直吹”；空调和热舒适产品决定具体风量、风向、出风温度及可用设备的组合。VCC 不应为每种车型重新维护这些域内控制细节。

### 4.3 判断功能归属的标准

当功能需要统一任务对象、跨域目标、共享生命周期、整体完成判定或统一降级协调时，放在 VCC 更合适。

一个系统能够独立完成的功能，仍可以由系统产品负责。即便统一通过 VCC 入口访问，也不意味着需要把实现、仲裁和状态机迁入 VCC。

例如：

- “把某个车窗设为指定开度”可以复用已有车窗产品的确定性能力。
- “为后排乘员营造安静、舒适且不打扰前排的休息环境”涉及多个目标与冲突，更适合由 VCC 承接为整体任务。

### 4.4 边界内组合的含义

用户提出的“有限能力范围内的任意场景组合”，可理解为：在已知能力、明确语义、允许的组合规则和当前适用条件内，按需形成未被提前枚举的场景。

这里允许出现新组合，但不能凭空产生新能力。已有的灯光与热舒适能力可以组合出新的个人场景；缺少对应执行能力、语义或验收方式的目标，不能仅凭模型生成一段调用描述就宣称支持。

### 5.2 外部 Agent 可以建议，VCC 负责承接

外部 Agent 可以提出目标组合、已有场景引用，甚至建议一个方案。VCC 需要结合车辆实际条件判断能否接受，并将接受的内容形成有边界的 Mission。

上游提出了方案，不等于车辆已经授权执行；VCC 接受了任务，也不等于任务已经完成。

### 5.4 不扩大到所有业务的总管

车控 Agent 的整体责任针对其承接的车控 Mission。一次用户请求可能同时包含导航、音乐内容和车控需求，顶层交互方仍可负责跨业务协调。

例如：“我有点冷，调整一下座椅，导航去目的地并播放舒缓音乐。”

- 座舱 Agent 处理整体交互和意图拆分。
- VCC 承接其能力范围内的热舒适、座椅或座舱环境目标。
- 导航目的地和路线业务继续由导航系统负责。
- 音乐内容选择继续由对应产品负责；如果音量或声环境属于某个车控场景目标，可按约定纳入协同。

同样，智驾系统的行驶决策和车辆运动控制权限，不会因为 VCC 更懂车就自动迁移到 VCC。涉及此类协同时，需要遵循对应系统的权责边界。

一个确定性手机界面可以发精确请求，也可以调用预定义场景。一个 Agent 同样可以发送精确请求。接口形态取决于需求语义，不取决于调用者是否被称为 Agent。

### 6.2 自然语言理解与车辆理解的分工

上游已经完成语音识别和用户意图理解时，VCC 不必重新进行一遍相同的通用 NLU。它应重点处理意图在当前车辆上的含义和可执行性。

例如，“后排有点冷”可以由上游表达为：后排特定乘员、改善热舒适、相对升温。VCC 再结合占座、设备可用性和已有任务判断如何满足。

原始文本可以作为解释和追溯的补充信息，但不应成为任意字符串直接驱动车辆执行的唯一依据。

### 6.3 请求同时表达了多少决策授权

“把灯光调到 30%”与“让后排适合休息”的授权范围不同。后者通常允许系统在约定能力范围内选择实现方式，前者应保持精确控制的范围。

来源身份、车辆绑定、乘员角色和权限应由可信的接入机制确认，不能直接相信模型自填的高优先级或高权限声明。上下文事件也应与授权请求分开表达。

对于已明确授权、规则清晰的常规请求，不必每次都要求用户确认；涉及歧义、硬约束冲突或超出授权的变化时，再进入澄清。

## 7. 场景能力与目标组合能力的关系

### 7.1 可以理解为场景能力，但场景不只是编号和脚本

目标组合能力可以承载场景能力。场景描述了在某种上下文中需要达到的整体效果，目标组合描述了这个效果由哪些目标和关系构成。

一个场景可以预先命名，也可以由请求动态形成。名称主要帮助识别、复用和产品化；可执行性的基础是其背后的能力和语义。

### 7.2 三种逐步扩展的表达

1. 预定义场景：编号加固定业务流程，适合高频、稳定且验证充分的需求。
1. 参数化场景：保留场景模板，同时允许指定对象、区域、偏好和约束。
1. 动态目标组合：在已知目标能力集合内，按请求组成新的场景。

三者可以长期并存。动态组合并不意味着放弃预定义场景，预定义场景也不应阻碍合理变体。

### 7.3 命中场景要看语义和条件

“我要午休”可以匹配预定义休息场景。但“我要午休，不要动座椅”，不能只命中“午休”关键词后执行原场景的座椅动作。

VCC 应先判断模板是否支持这个约束：支持则参数化复用；部分支持则保留可复用目标并重新组合；约束无法满足则说明冲突或提供替代方案。

因此，已知场景优先复用、必要时调整，通常比每次从零生成更符合可控性和可解释性要求。

## 8. 新场景如何通过稳定接口暴露

### 8.1 核心做法

**使用稳定的任务提交形式，传递可变长度的、具有明确类型的目标集合。预先定义表达目标的语义，不预先枚举所有场景。**

对外暴露的对象可以包括：

- 能力发现：支持哪些目标、适用对象、参数范围、约束和结果。
- 场景调用：引用已知场景及其参数。
- 任务提交：传递结构化目标组合。
- 任务交互：查询或订阅结果、补充信息、修改或取消任务。

这些是逻辑能力，不代表已经决定必须各自对应一个 RPC，也不代表全部消费者都需要同一种访问协议。

### 8.2 为什么不需要为每个场景新增 IDL

如果热舒适目标、灯光目标及区域等语义已经定义，就可以在同一次请求中同时携带这些目标。新的组合不需要新建“二排右侧暖一点且暗一点”专用接口。

但如果出现全新的能力概念，已有类型无法准确表达，仍然需要扩展能力语义、参数和结果定义。一个任意 JSON 容器并不能自动解决未知能力的问题。

### 8.3 外部表达目标，VCC 决定如何协调

外部请求通常应表达“要什么、针对谁、不能做什么、偏好什么”，而不是指定所有底层 RPC、执行顺序和设备细节。

如有业务上必要的先后关系，可以表达目标依赖；具体域内执行过程由系统产品完成。这样既保留动态组合空间，也避免每个调用方都要理解车型硬件和控制时序。

## 9. 结构化目标组合的完整例子

以下例子延续前面讨论，用于解释实际传递的信息。

### 9.1 用户需求

“二排右侧稍微暖和一点，灯光暗一点，不改变前排设置，尽量省电。”

这个请求包含：

- 热舒适目标：二排右侧稍暖。
- 灯光目标：二排右侧稍暗。
- 硬约束：保持前排热舒适和灯光设置。
- 软偏好：尽量省电。

### 9.2 请求内容示例
```json
{
  "request_id": "request-001",
  "goals": [
    {
      "goal_id": "goal-thermal",
      "thermal_comfort": {
        "area": "SECOND_ROW_RIGHT",
        "change": "SLIGHTLY_WARMER"
      }
    },
    {
      "goal_id": "goal-lighting",
      "lighting_comfort": {
        "area": "SECOND_ROW_RIGHT",
        "change": "SLIGHTLY_DIMMER"
      }
    }
  ],
  "constraints": {
    "preserve_settings": [
      {
        "area": "FRONT_ROW",
        "domains": ["THERMAL", "LIGHTING"]
      }
    ]
  },
  "preference": "ENERGY_SAVING"
}

```

这里没有场景编号，没有指定某个温度数值、风机挡位或底层接口，也没有要求调用方知道车辆如何分配共享热资源。

### 9.3 VCC 接到之后应理解什么

VCC 需要确认目标类型和作用区域是否受支持，判断当前基准和相对变化的含义，检查前后排是否共享不可独立调节的资源，以及是否有正在执行的冲突任务。

如果当前车辆确实无法在保持前排设置的同时改善二排热舒适，这属于硬约束冲突。VCC 不能为了满足“稍暖”静默改变前排；应说明不支持、提出可接受替代，或请求进一步选择。

“尽量省电”属于偏好，可以影响可行策略之间的选择，但不能凌驾于硬约束和系统保护之上。

“稍微暖一点”也必须具有双方理解一致的业务含义和评价方式，不能只定义一个字符串枚举而不定义含义。

### 9.4 接收回执与执行结果分开
```json
{
  "request_id": "request-001",
  "mission_id": "mission-1001",
  "admission": "ACCEPTED",
  "issues": []
}

```

该回执仅表示任务已被接受，后续应通过任务状态或结果反馈说明是否达成。

结果可以按子目标说明：热舒适目标已达成、灯光目标未达成、原因是什么、整体任务是否按规则算作部分完成。具体结果字段和状态机尚未冻结。

## 10. 对内编排与系统执行的关系

### 10.1 逻辑分层
```plaintext
座舱 Agent／智驾 Agent／手机／传统控制入口
                    ↓
         需求、目标、约束、上下文
                    ↓
        VCC：场景与 Mission 协调
                    ↓
      本域目标契约 → 系统产品／目标适配
                    ↓
      既有 SOA 动作、状态、事件及执行能力
                    ↓
           控制器与执行机构

本域结果与证据 → VCC 整体结果 → 请求方

```

这是职责关系示意，不要求这些逻辑层都独立部署为软件模块。

### 10.2 VCC 编排的主要内容

VCC 处理的是目标之间的关系：哪些可以同时进行、哪些存在依赖、哪些争用资源、哪些是必需项、哪些可以降级，以及用户修改或手动操作后任务如何调整。

例如，休息场景中的“更安静”和空气质量场景中的“加强通风”可能有冲突。VCC 需要决定整体目标如何协同；空调产品决定具体控制方式和域内限值。

### 10.3 复用现有完整功能

如果系统产品已经提供完整场景或目标型能力，优先复用其闭环执行。不能因为引入 VCC 就把同一功能拆成一堆低层动作重新实现。

如果现有系统仅提供动作和状态，则可在系统产品侧补齐目标解释和结果反馈。到底需要新增接口还是适配既有接口，要看具体能力缺口。

soa_adaptor 的职责仍是通信和 IDL 桥接。Mission 规划、业务仲裁和跨系统场景语义不应混入其核心桥接逻辑。

## 11. Mission 的完整责任：承接、运行与结果

### 11.1 不能混同的几个阶段

任务被接收、控制请求已发送、系统产品已接受、执行中、子目标达成、整体目标达成，属于不同含义。

FF 接口发送成功不能证明物理动作完成；RR 接口返回成功也要查看返回语义，可能只表示请求合法或已经接收。

VCC 的整体责任是对这些差异作出清晰表达，不把底层通信成功包装成用户目标已经实现。

### 11.2 需要覆盖的生命周期语义

目前可明确需要表达以下业务情况，但具体状态枚举尚未冻结：

- 接受、需要补充信息、拒绝。
- 运行中、目标已达到、维持中。
- 部分完成、降级完成、失败或结果未知。
- 被修改、被抢占、中断、取消或结束。

一次性目标与持续目标有所不同。“把灯光设为某值”可以达到后结束；“维持适合休息的环境”可能需要持续运行，直到明确终止条件成立。

取消任务也不等于物理撤销已经发生的动作。是否恢复、恢复哪些设置、以哪个基准恢复，要有明确策略，不能默认所有动作都可逆。

### 11.3 结果应有依据

任务和子目标需要能够关联请求、状态和结果。已有接口如果不携带请求关联信息，不能把任何一次状态变化都认定为本次请求导致。

例如，灯光状态达到了目标值，可能来自当前任务，也可能来自手动操作或其他控制源。整体判定需根据能力契约明确是“目标状态已满足”，还是“本次动作已经确认完成”。

### 11.4 soa_adaptor 调研带来的重要提醒

此前关于 SM 读取和 E2E 的确认，对未来结果判断有直接启发：

- 无 history queue 时，SM 周期读取可能一直返回 buffer 当前值，没有新数据标识。读取成功不等于源端本周期产生了新样本。
- 配置 history queue 时，读取会消费数据，没有新数据时返回空；周期内可以按队列中的数据逐项处理。
- 读取状态、实际数据和 E2E 状态是不同信息，不能相互伪造。
- E2E 状态应严格来自对应底座接口；业务如何处理错误由应用按需求决定。

因此，VCC 的结果契约需要按能力考虑状态来源、有效性、时效与证据，不能只看到一次接口返回成功就宣告任务完成。具体质量要求应由能力决定，不是所有业务都强制同一种 E2E 策略。

## 12. 场景的演进与伴生闭环

### 12.1 已认同的业务闭环

这些场景可以被记录为个人已知场景，通过伴生汇集使用情况和执行反馈，进而成为后续版本预定义场景的规划输入。

## 13. 现有 SOA、IDL 与 service_arch 能提供什么

### 13.1 可以复用的基础

已有平台 IDL 提供类型、字段、RPC 和通信模式，部署配置提供模块依赖、实例绑定和运行配置，源代码进一步揭示实际使用方式。

service_arch 可以作为服务、模块、实例、接口及源代码证据的架构资料基础，帮助建立能力到已有系统的映射。

可形成的追溯关系是：业务能力 → 目标和结果语义 → 所需服务接口与状态 → 实例及车型绑定 → IDL、代码与版本证据。

但静态架构事实不等于运行时可用性，IDL 也不能自动证明某个目标在实车上已经闭环实现。

第三类，当前系统没有对应功能或责任主体：需要建设真实产品能力，不能依靠 MCP 包装或通用 JSON 声称已经支持。

## 14. 协议选择：与业务能力契约分开讨论

是否复用服务接口、是否增加目标契约、是否采用 MCP 或 A2A，是不同层次的问题。

- 现有 SOA 接口承担稳定的车端执行和状态交互。
- 目标与结果契约定义车控业务含义和责任。
- MCP 等形式可以承载能力发现、结构化调用和工具接入。
- Agent 之间如需独立委托与任务协作，可以进一步评估 A2A 等方式。

无论采用什么协议，都仍需明确控制对象、授权、目标、硬约束、结果、生命周期和车辆可用性。

目前没有形成“必须采用 MCP”“所有 Agent 必须使用同一种协议”或“全面替换现有 SOA”的结论。更合理的研究顺序，是先稳定业务语义，再选择适合各类使用方的交互映射。

## 15. 相关场景举例

以下例子用于复述职责和机制，不作为已经上线的功能承诺。

### 15.1 预定义休息场景，带有特殊约束

用户说：“我要午休，但不要动座椅。”

座舱 Agent 识别休息需求和座椅约束。VCC 检查已有午休模板是否允许不调整座椅；如果允许，保留灯光、声环境和热舒适等适用目标，按参数化场景执行。

如果模板必须依赖座椅调整才能满足某些承诺，则说明差异或提供替代，而不是忽略用户约束。

这个例子体现：场景匹配依据需求和适用条件，预定义场景能够被复用和调整。

### 15.2 二排稍暖、稍暗，不打扰前排

对应第 9 节的 JSON 示例。VCC 组合热舒适与灯光目标，检查共享资源和区域独立能力，在保持前排设置的约束内协调执行。

如果只能满足灯光而不能满足热舒适，应该明确部分可行与冲突原因，由既定策略或用户选择决定是否继续。

这个例子体现：未命名的新场景可以由已知目标类型组合表达。

### 15.3 孩子休息，同时即将进入隧道

座舱 Agent 提供：二排孩子正在休息，希望保持安静。智驾或环境系统提供：即将进入隧道、可能存在空气质量变化，并注明预测来源和时效。

VCC 结合当前热舒适任务、空气质量、设备能力与授权，决定是否调整已有休息 Mission 的目标关系，并协调相应系统产品。

安静和通风可能冲突，VCC 负责解释与整体取舍，系统产品负责本域策略。离开该环境后是否恢复、恢复到哪里，也属于任务策略，而非默认回放相反动作。

这个例子体现：座舱、智驾和车控各提供自身擅长的信息与能力，车辆控制协调由 VCC 统一承接。预测本身不自动构成执行授权。

### 15.4 手机精确控制与语音模糊目标

手机用户选择某个车窗开度，属于精确控制；语音用户提出“有点闷，通风一下”，属于效果目标。

前者应保留确定的对象和范围，不能自行扩展成一套大场景；后者可在授权能力内选择通风方式，但仍须考虑车辆状态、环境及已有任务。

二者可以复用相同的底层产品能力，但外部语义和决策授权不同。传统界面不需要因此被迫经过 LLM。

### 15.5 远程出发前预调节与能量限制

用户希望上车时更舒适，同时要求尽量省电。VCC 可承接出发前舒适准备目标，结合车辆唤醒条件、SOC、设备可用性和当前模式判断可行方案。

若能量条件限制部分子目标，需要返回降级范围及原因。不能因为用户提出整体舒适目标，就绕过系统产品的能量保护和运行条件。

这个例子体现：目标可以统一承接，策略选择和硬保护仍然分层。

### 15.6 复合语音中的业务边界

用户说：“有点冷，调整座椅，导航回家并播放舒缓音乐。”

座舱 Agent 负责整体交互，导航与内容业务由各自产品承担。VCC 对其接受的热舒适和座椅等车控目标负责，而不是自动取得导航、互联网和所有娱乐业务的执行权。

这个例子体现：VCC 的端到端责任有明确承接范围。

### 15.7 保护类功能与常规体验场景

VCC 规划资料包含碰撞、热失控、儿童遗留等相关功能讨论。这些功能需要按各自的安全、实时性和控制权限明确归属。

不能因为统一讨论车控 Agent，就把保护动作强制放入生成式推理或等待用户对话的链路。可以在适当范围共享任务信息、状态和结果，但具体保护闭环仍按对应系统要求执行。

这个例子体现：统一业务视角不等于统一所有实时执行路径。

## 16. 与已有 VCC 业务规划的对应理解

参考文档《Vehicle Cabin Control (VCC) function architecture_0.0.1(WIP)》包含显式命令、场景识别、意图理解、任务建立、任务仲裁、异常处理、跨域规划以及座舱状态模型等内容。

它支持本次讨论的主要判断：VCC 依赖系统能力完成端到端任务，对场景目标、任务过程和整体结果建立责任，而不只是把服务调用汇总到一个入口。

### 16.1 功能链的对应

- 感知合理性检查、多源融合与上下文结构化，为目标判断提供事实基础。
- 显式命令与非命令场景识别，支持用户主动请求和基于上下文的主动服务。
- 意图仲裁与目标理解，将需求转换为期望的座舱状态。
- 任务创建、子系统任务定义、任务仲裁与异常处理，承接 Mission 生命周期。
- 跨域目标规划与系统反馈，支撑整体协调和完成判断。

### 16.2 NCM 与 ACE 的作用

NCM 可理解为支撑座舱理解和决策的状态、估计与上下文基础。ACE 中的安心、舒心、省心体现产品价值方向，但这些价值表达本身不能直接替代某次任务的可判断完成条件。

例如，“更舒心”需要落实为本次任务中明确的热舒适、噪声或空间等目标及其评价方式，才能对外反馈结果。

### 16.3 原规划仍有需要澄清的表述

资料中“具体控制目标与运动时序规划”“各子系统的具体执行”等表述，后续需要与系统产品的域内策略和执行边界统一。

本文采用已经讨论认同的边界：VCC 负责跨系统目标与协调；系统产品负责本域策略、时序、控制闭环和保护。不能仅凭功能框图名称就认定实现细节已经划分完成。

同时，原文是 WIP，且“个人理解简述”等内容具有讨论性质。本文引用其架构思路，不把所有段落视为已批准的正式产品基线。

## 17. 行业材料带来的借鉴

用户提供的关于大量 SOA 接口与大模型动态编排的文章，提供了一个值得参考的方向：已有服务化能力可以成为智能体满足复杂需求的执行基础，场景不必全部提前写死。

更适合本项目吸收的结论是：以现有 SOA 为基础，开放有业务含义、可约束、可反馈的目标能力，并由 VCC 承担车控任务责任。

不能从接口数量直接推导出 Agent 能力成熟度。接口很多，仍可能缺少目标语义、当前可用性、冲突处理或完成证据；最小粒度接口也不必然最适合外部调用。

因此，本次认同的方向是受约束的目标组合，不是让模型自由调用全部底层接口。并发调用不能替代系统时序和互斥处理，服务化与 OTA 也不会自动保证任意新增功能或离线推理能力。

该文章的具体车型、接口数量、模型部署和量产实现细节未独立核实；本文仅将用户提供正文作为架构观点参考，不将其中营销或实现描述作为已验证事实。

## 18. 已明确与尚待明确的分界

### 18.1 已形成关键结论

- VCC 提供边界内的场景与目标组合能力。
- 预定义场景、参数化场景和动态组合并存。
- 动态场景通过已知目标语义的组合表达，不依赖逐个枚举场景编号。
- VCC 对承接的 Mission 负责，系统产品保持本域执行责任。
- 车控相关跨系统编排与目标仲裁更适合由 VCC 统一承担。
- 座舱、智驾和车控按用户理解、外界理解和车辆响应分工协作。
- 现有 SOA 优先复用，是否重封装由语义和结果缺口决定。
- 场景可通过使用反馈、个人沉淀和伴生逐步演进为产品能力。

### 18.2 后续仍需讨论的事项

1. 首批对外能力边界：哪些目标可以稳定承诺，哪些只提供精确控制，哪些不应开放。
1. 目标语义与验收方式：相对变化、舒适效果、持续维持和部分成功如何定义。
1. 控制权与仲裁规则：不同请求源、乘员、远程入口、自动场景与手动操作如何协调。
1. 组合规则：哪些目标可组合、哪些有依赖或资源冲突，硬约束无法满足时如何处理。
1. 结果证据：哪些现有接口足够，哪些缺少关联、时效或可信完成反馈。
1. 场景记忆与产品化：什么条件下成为个人已知场景，如何评估为预定义场景。
1. 状态与任务生命周期：修改、取消、抢占、恢复和结果未知的正式语义。
1. 接入方式：不同消费方分别采用哪些服务或 Agent 协议，版本和车型差异如何表达。

这些是业务和契约进一步明确的议题，不意味着本文要求现在进入开发。

## 附录 A：结构化目标接口的 Proto 示意

以下定义复述此前技术讨论中的最小表达，用来解释“固定目标类型、可变目标组合”。它不是正式平台 IDL，没有加入平台 SOA options、部署信息或完整产品状态机，暂不作为可集成接口。
```protobuf
syntax = "proto3";

package vcc.example;

enum Area {
  AREA_UNSPECIFIED = 0;
  FRONT_ROW = 1;
  SECOND_ROW_RIGHT = 2;
}

enum Domain {
  DOMAIN_UNSPECIFIED = 0;
  THERMAL = 1;
  LIGHTING = 2;
}

message ThermalComfortGoal {
  enum Change {
    CHANGE_UNSPECIFIED = 0;
    SLIGHTLY_WARMER = 1;
    SLIGHTLY_COOLER = 2;
  }
  Area area = 1;
  Change change = 2;
}

message LightingComfortGoal {
  enum Change {
    CHANGE_UNSPECIFIED = 0;
    SLIGHTLY_DIMMER = 1;
    SLIGHTLY_BRIGHTER = 2;
  }
  Area area = 1;
  Change change = 2;
}

message Goal {
  string goal_id = 1;
  oneof target {
    ThermalComfortGoal thermal_comfort = 2;
    LightingComfortGoal lighting_comfort = 3;
  }
}

message PreserveSettings {
  Area area = 1;
  repeated Domain domains = 2;
}

message MissionConstraints {
  repeated PreserveSettings preserve_settings = 1;
}

enum Preference {
  NO_PREFERENCE = 0;
  ENERGY_SAVING = 1;
}

message MissionRequest {
  string request_id = 1;
  repeated Goal goals = 2;
  MissionConstraints constraints = 3;
  Preference preference = 4;
}

message MissionReceipt {
  enum Admission {
    ADMISSION_UNSPECIFIED = 0;
    ACCEPTED = 1;
    NEEDS_CLARIFICATION = 2;
    REJECTED = 3;
  }
  string request_id = 1;
  string mission_id = 2;
  Admission admission = 3;
  repeated string issues = 4;
}

service VehicleCabinControl {
  rpc SubmitMission(MissionRequest) returns (MissionReceipt);
}

```

这个例子只包含两个目标类型和任务接收回执。正式契约还需按业务需要定义能力发现、任务状态与结果、必要的目标关系及交互机制。是否使用 Proto，以及如何映射到现有平台，仍未冻结。
