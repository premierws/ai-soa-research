01规划建议

服务架构矩阵
怎样支持车控智能化

基于现有 SOA，改进服务设计、通信机制、开发工具和测试方法。

V2.3 · 图解版2026.11.17

重点说明：需要改什么、由谁负责、交付给谁、如何验证。

本版以 V2.1 和 V2.3 为基础重写表达及图示。保持服务架构矩阵的 SOA 专业范围，不接管独立软件架构矩阵的职责。
0201 / 要解决的问题

接口能调用，还要知道怎么用、是否做成

VCC 使用车控服务时，需要同时了解调用条件、实际状态和执行结果。

这里讨论的是服务接口及其运行要求，不推定所有请求必须由大模型处理。一次精确命令可以直接走确定性调用。
0302 / 规划主线

从具体功能需求，推导 SOA 改进项

不先建设新平台；先确认现有服务能否满足需求。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
0403 / 架构关系

VCC 组合功能，系统产品完成控制

SOA 提供通信和服务使用机制，不替代业务决策。

图中是功能及服务的关系，不是新的进程或部署方案。原子服务、控制算法和执行器链路继续保留。模块划分、运行及部署由软件架构责任组织确认。
0504 / 两条建设线

一条改进服务设计，一条改进技术底座

服务设计解决“怎么用”；技术底座解决“能否稳定、高效地运行”。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
0605 / 接口设计

服务接口规范，要写清六件事

IDL 定义消息结构；功能说明和接口规范补齐业务含义。

能力描述在本材料中指服务功能、使用条件及反馈的说明，不要求增加独立的运行平台。FO/SO 确认功能与物理限制，矩阵制定共用写法，领域团队维护具体接口。
0706 / 调用流程

请求已受理，不等于执行已完成

按业务需要选用 RR、FF、Event 和 Field，不强迫所有接口采用同一种形式。

这是存在异步执行和受理反馈时的语义示意。FF 没有 RR 回包；可通过已有状态或单独结果通知反馈。RR 返回或可靠传输 ACK 均不自动证明物理效果。
0807 / 结果判断

状态满足目标与本次请求执行成功，要分开判断

请求关联、实际状态和数据质量共同决定可以报告什么。

状态机表达逻辑上的结果区别，不要求每个精确控制接口实现完整任务状态机。持续任务还需定义修改、暂停、取消和人工操作处理。
0908 / 通信质量

读到缓存，不代表收到新数据

分清 API 调用结果、数据时间、通信质量和业务状态。

无 history queue 的 SM 可能每次返回 buffer 当前值且没有更新标识。底座没有提供的时间或 E2E 信息不能伪造。E2E 配置、暴露与业务处理按已确认需求决定。
1009 / 专业工作

六项专业工作，都要形成可使用的输出

用明确的规范、代码样例、配置检查和测试用例支持业务团队。

六项名称是对原六个工作方向的直白表达，不要求分别设立六个部门或同时启动六个平台项目。
1110 / 需求追溯

每项需求，都能找到输出、使用团队和测试

保留这一张追溯表，用于后续任务分解和检查。

1211 / 组织形式

矩阵是专业协作组织，不是新的软件开发部门

稳定核心负责规范和技术方向，领域代表带来需求和工程经验。

AI 在此指车型架构角色。参与矩阵不改变所属团队责任，资源和交付仍由相应组织确认。
1312 / 职责边界

功能、接口、软件设计和代码实现分别负责

矩阵研究服务接口及 SOA 机制，整体软件架构由独立矩阵负责。

图表示职责之间的输入输出，不增加固定串行审批。车型架构 AI 确认整车功能分配和车型差异。技术建议不能替代产品或项目承诺。
1413 / 工作流程

围绕一个真实问题，完成设计、试验和推广

业务需求和底座问题都可以进入；每个专题有明确负责人。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
1514 / 案例 A：正常调用

二排暖一点，前排设定不变

先定义“暖一点”与完成条件，再设计接口和调用流程。

接口名、参数和达成条件需具体功能设计确认。这里不是用某个固定温度值代替主观舒适，也不是由 VCC 直接设置风机或压缩机闭环参数。
1615 / 案例 A：工程分工

从功能设计到实车测试，每一步都有责任方

矩阵交给业务的是接口规范和验证方法，工程团队实现并测试。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
1716 / 案例 B：运行中变化

除雾请求或手动操作出现后，任务怎样处理

VCC 负责调整任务，系统产品保持本域仲裁和保护。

除雾、用户操作的具体优先级由功能责任方确认，不能由底座统一猜测。取消后是否恢复以及恢复什么设置，要单独设计。
1817 / 案例 B：状态检查

先区分“失败”和“不知道”，再反馈给用户

检查来源状态、数据时间和执行结果，不能靠缓存值宣布成功。

API 读取失败、通信 E2E 状态与业务执行失败属于不同信息。需要哪些检查由具体功能决定，不对全部订阅统一强制 E2E 门控。
1918 / 案例 C：OTA 后复用

接口名没变，也要检查行为和配置是否变化

个人场景保存目标和限制，不能只保存一串设备动作。

矩阵定义版本关系和检查方法，工具团队维护分析工具，产品定义语义兼容，VCC 处理个人场景是否继续。发布与整车回归仍归对应责任组织。
2019 / 案例 C：版本关系

把功能、服务、配置和测试用例关联起来

变化发生后，能够查到受影响的场景和需要重跑的测试。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
2120 / 采用与评价

完成一份规范，不等于业务已经用好

分别检查接口质量、使用成本和实际功能效果。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
2221 / 推进计划

先把一类功能做清楚，再扩大使用范围

根据功能需要和测试结果推进，不按年份要求所有方向同时完成。

本页为规划建议，责任人员、试验条件和项目投入需由相关团队确认。
2322 / 本轮建议

先确认三件事，便于开始具体工作

方向保持 SOA 专业定位；项目开发、版本和资源由对应组织确认。

本轮不承诺新的量产能力，不预设新增运行平台，也不把所有软件架构职责移入服务架构矩阵。
