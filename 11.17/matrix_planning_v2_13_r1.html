03第1部分 / 1.1 业务目标

在已有系统服务基础上，扩展场景协同能力

在NOMI理解和表达用户需求的基础上，提高车辆对实际使用条件的适应能力。

减少反复调节与跨系统协调负担，使体验更合适、稳定、可控；组合与编排是实现手段。
SDV材料提出SOA—能力—Agent的演进方向；本轮讨论明确预定义和受约束自适应场景并存。图表示功能层次，不是新增进程或部署方案。
04第1部分 / 1.2 五层功能架构

车控Agent功能架构：承接需求，组织场景执行

以场景能力服务为主要入口，向下分发控制任务，向上汇总状态与执行结果。

明确控制输入可调用基础能力接口，按必要路径仲裁和执行；任务运行管理包含异常与故障处理。
五层为功能职责，不规定软件进程与部署。基础能力虚线表示明确控制不必触发完整场景规划，但仍需必要权限、仲裁和系统校验。硬开关经既有适配形成明确请求，不表示所有实时硬件链路改经Agent。系统保护不等待Agent批准。场景和系统例子取自已有VCC规划。 接入、组织协调仲裁、任务分解与运行管理三层共同组成车控Agent主体，使用统一背景框表示；用户意图识别层与系统执行层在主体外。

06第2部分 / 2.1 对外接口

对外接口：场景能力为主，兼容明确的基础控制

用户意图识别层通过服务接口接入；明确控制输入也可直接调用基础能力。

条件与规则写入接口定义及使用说明，不要求每次请求传入整套规则；执行侧仍进行相应校验。
接口形态为服务调用及必要的状态/结果反馈；具体METHOD、EVENT、FIELD组合按业务设计。可参考AiCabin已有场景请求、取消表达、推荐和状态接口，但不推定现有状态语义与请求关联已经完整。NOMI提供需求与确认，不作为车辆可执行性的唯一检查者。
07第2部分 / 2.2 内部职责与交互

内部协同：协调层定方案，任务层管理，系统层执行

场景请求逐层落实为系统任务，系统状态与限制逐层支撑判断和结果汇总。

整体场景判断通过不替代系统校验；基础控制路径可以简化，但不绕过必要仲裁和本域保护。
协调层处理跨系统整体方案，任务层处理执行组织、状态与异常流转；任务层可依据反馈请求协调层重新决策。系统内部时序和实时保护留在系统产品。不是所有响应都要依次等待五层处理。
08第2部分 / 2.3 运行反馈与异常处理

运行管理：依据系统反馈，调整、中断或退出场景

异常与故障处理位于任务运行管理层，并与协调层决策、系统本域保护配合。

系统实时保护不等待Agent批准；退出请求不等于已经停止，条件恢复后是否恢复场景需重新判断。
三种情况是按五层职责展开的场景行为说明，不是发生任何异常都退出。按影响和业务规则处置；信息不足不伪造可执行或完成。条件、策略与时限由业务和系统确认。

12第3部分 / 3.3 车控Agent外部交互语义

车控Agent外部交互语义：统一请求与执行反馈

目标：使用方能够明确发起、跟踪、调整和结束任务，正确理解实际执行结果。

形成成果外部交互规范、时序与参考接口
重点支撑用户意图识别层与Agent接入层
验证与采用接受不等于完成，取消请求不等于已停止
本页区别于场景定义：定义使用方与服务之间的交互，而非重述场景内部策略。基于已有接口核查任务关联、取消对象、部分结果等是否足够，不直接宣称现有框架均不支持。图示第三条为修改/取消请求，实际处理结果沿向上的反馈通道返回。
13第3部分 / 3.4 通信中间件基础能力需求

通信中间件基础能力：以场景运行要求牵引提升

目标：可靠传递控制、状态与结果，满足异常处置所需时序，并合理使用资源。

形成成果有业务来源的平台机制与性能需求
重点支撑各层控制分发、执行反馈与异常协调
验证与采用系统保护独立保留，平台方案联合验收
场景协调不替代本域实时保护。具体需求可涉及服务可用性、事件/状态传递、请求关联、队列、QoS、端到端时序和失效行为。现有能力是否满足须通过目标环境测量。不预设新协议或中间件，不编造性能数字。
14第3部分 / 3.5 基础服务自适应编排

基础服务自适应编排：建设能力与约束的共同基础

目标：基础服务可识别、可组合，车控Agent能够在允许范围内选择方案并按变化调整。

矩阵建设描述、规则与工具；系统供给能力和约束；VCC负责具体场景的方案选择与运行决策。
原平台IDL显示抽象层次不一，部分仍体现底层布局，已有空间与热舒适高层接口应复用。矩阵不包办Agent规划算法，也不将基础服务改造成自由调用且无约束的动作库。参考实现不预设新增独立运行平台。
15第3部分 / 3.6 团队与资源安排

团队与资源：按专题共建，明确投入与维护责任

四项能力需要业务、系统和平台共同建设，并落实到责任人、参与时间和验证环境。

虚拟矩阵组织共性建设；不替代业务开发、系统保护责任或独立软件架构组织。
本页明确资源种类和协作责任，不编造人数、工时或交付日期。各专题应有业务负责人、技术负责人、采用团队、评审/验证出口及成果维护安排。平台与领域架构师按既有组织分工协作。

17第4部分 / 4.1 组织与职责

组织运营：以常驻骨干统筹，按专题组织共建

围绕四项能力落实专业负责人，由业务、系统和平台团队共同提出需求、建设与采用。

组织形式为改进建议。继承原矩阵常驻架构骨干、其余按议题参与的机制；按现行公司角色更新表达。专题不是新设行政组织，成员投入与责任由所属团队承诺。
18第4部分 / 4.2 议题接收与成果闭环

议题闭环：从需求接收到成果采用

沿用议题登记、方案评审和责任团队实施流程，补强采用验证与成果维护。

紧急故障与安全风险立即进入责任团队处置流程，矩阵并行支持，不等待例会。
合并原接收、评审、采用三页。继承原三类评审结论（通过、有条件通过、不通过），不通过回到方案修订；有条件通过需满足对应条件。矩阵决策不替代既有服务变更和发布审批。成果按性质安排验证，规范类以试点使用验证，代码类按范围完成集成运行验证。
19第4部分 / 4.3 冲突上升与日常运营

协调运营：冲突有决策路径，行动有跟踪闭环

专题内先协调，超出权限或影响关键计划时上升；TPM维护统一记录，责任团队落实行动。

沿用周或双周例会；安全与保护要求按既有责任机制处理，不以矩阵表决放宽。
以原矩阵例会、TPM运营、关键技术方案上升和跨矩阵协作为基础。分流路径及改进运营为建议机制；现行授权组织名称与责任人需确认。决策记录包含理由、适用条件、责任及后续验证。周期复盘以四项能力投入、采用进展和反复问题改善为依据，不新增强交付职责。
