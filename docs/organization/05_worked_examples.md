# 角色协作案例

日期：2026-11-13。以下用于解释职责和交互，不是新增功能承诺或已完成工程验证。

## 1. 二排稍暖，不改变前排设置

### 业务问题

用户或外部 Agent 提出二排右侧稍暖，要求保持前排设置。需要把模糊目标、共享资源、车型差异和结果反馈贯通起来。

### 角色交互

1. VCC FO 提供整体场景、对象、约束和 Mission 反馈要求。
2. 热舒适 FO 定义“稍暖”的功能含义、本域行为及达成条件。
3. 热舒适 SO 判断区域独立调节能力、风道与热资源共享、可用设备和承诺范围。
4. AI 判断不同车型的系统分配和配置差异。
5. 领域软件架构师判断现有热场景接口的复用方式，以及输入、关联和结果缺口。
6. 平台软件架构师研究可复用的目标接收、状态结果和错误表达机制。
7. SWE 与验证工程师通过实际实现或小规模样例检查关键假设。
8. COE 沉淀能力契约、服务映射、适用条件和验证方法，供 VCC 与其他业务采用。

### 必须澄清的歧义

“不影响前排”可以指前排设置不变，也可以指前排实际热环境不变。FO 应明确含义，SO 判断能否实现；不能由软件自行选择解释。

共享资源导致硬约束不可满足时，应说明冲突或提出替代。是否接受替代由相应授权和业务策略决定。

### COE 的闭环

这项工作即使不立即产出量产代码，也应留下可采用、可验证的技术成果。正式开发由相应组织承接。

## 2. SM buffer 与状态质量：工程事实修正架构

此前 soa_adaptor 研究确认，无 history queue 的 SM 读取可能始终返回 buffer 当前值，没有新数据标识。读取成功不等于源端产生新帧；E2E 状态需来自底座实际状态通路。

在 COE 中，SWE 提供真实 API 行为和试验证据；平台架构师检查共用状态语义；领域架构师与 FO 判断业务如何使用；验证工程师区分能验证哪些行为。

由此形成的共性方法是：读取结果、数据更新、状态时效和质量信息分别表达；不能通过抽象掩盖底座没有提供的信息。

已有佐证见 [Demo README 快照](../../evidence/soa_adaptor/README.md)。这不是本次新做的验证，也不意味着所有能力必须使用同一种 E2E 门控。

## 3. 休息需求与车外态势输入

座舱侧识别孩子休息需求，智驾或环境系统提供即将进入隧道的预测，VCC 协调安静与空气质量目标，系统产品完成通风等本域策略。

COE 在这个问题中的价值，是组织不同团队共同明确：

- 座舱侧提供怎样的需求、对象、约束和授权。
- 智驾侧提供怎样的预测、来源和时效。
- VCC 承接哪些控制决策和 Mission 责任。
- 系统产品可以承诺怎样的目标与结果。
- 底座和软件机制怎样传递状态、关联和异常。

COE 提供共同契约和协作方法，不代替任一 Agent 做运行时业务决策。预测本身也不自动构成控制许可。
