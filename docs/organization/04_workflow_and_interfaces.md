# 工作流、交互界面与确认责任

日期：2026-11-13。以下是 COE 运作建议，不把技术议题流程视为新增车型发布审批流程。

## 1. 议题工作流

| 阶段 | 主要牵引角色 | 输入与活动 | 输出 |
| --- | --- | --- | --- |
| 问题提出 | FO、SO、架构师或 SWE | 具体场景、当前困难、影响团队、已有证据 | 问题描述与研究边界 |
| 功能与边界澄清 | FO＋SO，AI 参与 | 需求目标、系统条件、职责及车型差异 | 目标、约束、责任主体、完成条件和适用范围 |
| 共同方案研究 | 平台＋领域软件架构师 | 契约、领域分工、服务现状、底座约束 | 交互与能力方案、服务提升模式、底座需求 |
| 工程与验证评估 | SWE＋验证工程师 | API 行为、资源代价、环境及可验证性 | 可行性结论、试验与验证依据、限制 |
| 技术共识形成 | 相关责任角色 | 方案选择、取舍、分歧和证据 | 采用方向、适用条件、未决问题与演进建议 |
| 资产沉淀与应用反馈 | 对应技术资产负责人 | 可复用成果与实际采用情况 | 规范、模式、样例、工具需求、应用反馈 |

COE 的闭环是：问题讲清楚、方案有依据、共同能力被沉淀、业务能够采用。对外正式工程开发与发布依照现有组织承接。

## 2. 关键角色间交互

| 双方 | 前者提供 | 后者提供／校验 | 共同形成的结果 |
| --- | --- | --- | --- |
| FO ↔ SO | 功能需求、目标、正常异常表现、完成条件 | 系统能力、物理资源、运行条件和限制 | 可兑现的能力承诺 |
| AI ↔ 软件架构师 | 整车功能分配、控制器协作和车型约束 | 软件职责、服务关系、部署机制、资源与时延影响 | 整车分配与软件方案一致 |
| 平台 ↔ 领域软件架构师 | 可复用关联、状态、错误、生命周期与诊断机制 | 领域目标语义、执行反馈、接口映射及真实缺口 | 共性机制与领域语义的边界 |
| 架构师 ↔ SWE | 架构假设、契约、约束与预期行为 | 实际 API、运行行为、资源及工具链限制 | 经工程证据校验的抽象 |
| FO／SO／架构师 ↔ 验证工程师 | 功能与契约承诺、适用条件 | 验证方法、环境能力、结果及证据限制 | 可以验证的能力定义 |
| COE ↔ DO | 已研究的技术方案、依赖及限制 | 集成、版本、发布和实际交付中的约束 | 需要时的工程承接衔接 |
| 议题负责人 ↔ TPM | 问题、参与方、行动项和分歧 | 记录、协调、提醒和升级支持 | 可追溯的技术议题运作 |

## 3. 四个重要界面

### 3.1 FO 与 SO

FO 定义用户需要什么和功能应如何表现；SO 判断本系统能否承诺以及受到什么限制。模糊需求不能直接留给软件自行解释。

### 3.2 AI 与软件架构师

AI 关注整车及车型功能如何分配，软件架构师细化软件职责和运行机制，并反馈实现代价。两者持续相互校验。

### 3.3 平台与领域软件架构师

平台维护共性机制；领域维护目标含义和本域执行关系。平台不替领域决定功能，领域不各自重造相同基础机制。

### 3.4 架构师与 SWE

SWE 尽早参与，使用实际实现和试验修正假设。方案不是只由架构师写完后单向交给实现。

## 4. 决策与确认

| 内容 | 应确认的责任主体 |
| --- | --- |
| 需求、功能表现和能力承诺 | 相应 FO／SO |
| 车型及整车架构分配 | AI |
| 软件架构和共用契约 | 对应平台／领域软件架构师及参与责任方，在授权范围内形成共识 |
| 验证结论和证据范围 | 相应验证责任方，并与功能责任方对齐 |
| 工程投入、版本和交付节点 | 对应业务、平台和项目组织 |

正式授权范围尚需公司机制确认。意见不能收敛时，应保存分歧、方案和证据，并进入既有决策机制，而非默认 COE 可以覆盖其他责任主体。

## 5. 知识资产和应用反馈

每项能力模型、契约规范、服务提升模式和底座需求方法应有具体维护人或团队，维护版本、适用范围和变更理由。

组织输出不止会议结论，还包括可供业务采用的样例和方法。业务采用后出现的问题应回到 COE，用于修正规范和共性方案。

动态场景在已发布的能力与组合规则范围内运行，不需要把每个新组合都提交矩阵评审。新增能力语义、授权或突破既有边界的变化，再进入对应技术决策与业务确认。
