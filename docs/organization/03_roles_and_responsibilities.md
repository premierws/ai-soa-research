# 虚拟 COE 的角色与职责

日期：2026-11-13。角色含义按用户提供的公司体系记录。AI 指车型架构角色，不是人工智能模型。

## 1. 组织组成

| 参与层次 | 角色 | 参与方式 |
| --- | --- | --- |
| 稳定核心 | AI、平台软件架构师、领域软件架构师，VCC 与关键系统的 SO／FO 代表 | 持续维护方向、边界、共用契约、架构原则与能力建设议题 |
| 领域代表 | 各相关系统 SO、FO、平台及领域 SWE | 稳定对接本领域，参加相关研究和评估 |
| 按议题参与 | 测试验证、算法与数据工程师、DO、相关专项专家 | 提供议题所需的证据与专业判断 |
| 运营支持 | TPM，可兼职 | 议题、结论、行动项与知识资产索引维护 |

层次表示参与方式，不是新设行政层级。核心不必覆盖所有系统，但要具有功能、系统、车型、软件架构和实现视角。

## 2. 各类角色

| 角色 | 公司角色含义 | 在 COE 内的职责 | 典型贡献 |
| --- | --- | --- | --- |
| SO | 负责软硬件子系统 | 明确系统能力边界、物理与软硬件约束、跨系统依赖，判断能力承诺是否成立 | 能力边界、资源冲突、系统适用条件和演进建议 |
| FO | 功能需求承接和详细设计 | 将业务需求转成目标、场景、正常与异常行为、完成条件 | 功能详细设计、目标和约束、功能验收条件 |
| AI | 车型架构方案 | 判断整车及车型功能分配、跨系统与跨控制器协作及车型差异 | 整车分配、车型适用性、架构约束 |
| 平台软件架构师 | 平台软件架构 | 定义共性软件机制、中间件与底软边界和功能性能需求 | 通用交互、状态错误语义、生命周期机制和底座需求 |
| 领域软件架构师 | 领域软件架构 | 将能力映射到本域软件，明确服务组织、目标适配和接口演进 | 领域方案、服务映射、复用及迁移策略 |
| SWE | 软件实现 | 用实现经验检验方案，揭示 API、工具链、资源和运行时限制，参与必要试验 | 可行性评估、参考样例、POC、工程反馈 |
| DO | 交付 | 提供进入实际交付体系的依赖、版本和集成要求 | 交付约束、承接衔接和应用问题；按议题参加 |
| TPM | 项目管理 | 支撑跨团队技术组织运营与问题升级 | 议题台账、会议记录、行动跟踪、协同 |
| 测试／验证工程师 | 按公司已有岗位映射 | 判断怎样证明契约成立，区分 Mock、仿真、台架、实车的证据范围 | 验证策略、通用用例、证据边界与评估 |

算法和数据工程师等按需要参与，不在本次讨论中强行设为所有议题的固定岗位。

## 3. 角色参加矩阵后的责任关系

各角色保留在业务组织中的专业责任。加入矩阵意味着参与共同问题研究、形成跨团队共识，并将成果带回本领域应用。

不能用矩阵身份替代系统能力承诺，也不能由矩阵会议自动承诺量产版本、工程资源或项目节点。

## 4. 三种需要明确的责任

- 业务责任：相应 FO／SO 确认需求、功能语义、能力承诺和业务验收。
- 架构责任：AI 及对应软件架构师确认分配、边界、契约与共性方案。
- 工程交付责任：当研究进入正式开发，由相应实现、交付组织明确承担。

这三种责任是议题分工，不要求新增三个岗位，也不要求 COE 成为第三类责任的归属主体。

## 5. VCC 和其他使用方的参与

VCC 应由相应 FO、SO、领域软件架构师参与，而不只是单向提出需求：FO 明确整体场景与 Mission 行为；SO 明确系统责任；领域软件架构师明确编排和运行的软件要求。

热舒适、座椅、灯光等产品的相应角色确认子目标承接和反馈。座舱、智驾、手机等相关团队在交互契约议题中参与，使需求、车辆执行和软件可实现性相互校验。
