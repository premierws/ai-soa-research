# 组织定位与责任边界

日期：2026-11-13。

## 1. 重新规划的前提

用户澄清：原技术规划的大多数条目已经达成、可以关闭。旧业务规划用于理解已有基础，不应使新规划过多围绕历史工作的继承展开。

现有基础包括服务接口、组织管理机制、服务交付经验、平台方案，以及 service_arch、soa_adaptor 等相关技术积累。新的研究问题是：如何利用这些基础，提升组织和平台能力，赋能 VCC 等团队实现车控 Agent。

## 2. 建议的使命

构建面向智能体的车控能力架构与技术平台，统一能力交互契约，提升既有服务的可理解性、可组合性和可验证性，推动底座能力演进，赋能 VCC 等业务团队实现受约束的目标组合与任务闭环。

上述是本次讨论采用的使命方向，不是正式组织名称或已经批准的章程。

## 3. COE 的定位

用户进一步强调：该技术组织是虚拟组织，更接近能力中心 COE，没有强交付属性。

据此，矩阵对共同技术能力、架构原则、方法、规范和知识资产负责。量产软件、车型版本、项目节点以及相应工程交付继续保留在既有业务和项目组织。

矩阵通过跨团队协作解决单个团队难以独立解决的问题，并使方法和共识回到各领域应用。COE 仍需要检查成果是否可采用、假设是否有依据、问题是否得到解释，但不自动接管项目排期和量产交付。

## 4. 服务对象

| 对象 | 主要赋能内容 |
| --- | --- |
| VCC 等业务团队 | 能力可用范围、目标组合规则、任务交互、可信状态与结果、开发验证方法 |
| 系统产品团队 | 本域能力表达、目标及结果契约、既有服务提升方案、接入模式 |
| 中间件与底软团队 | 来自真实业务的功能性能要求、机制边界及验证依据 |
| 座舱、智驾、手机及传统使用方团队 | 共同交互语义、授权范围、上下文交换和结果解释 |

## 5. 三类主要责任

| 主体 | 责任 |
| --- | --- |
| VCC／业务团队 | 场景、任务编排、跨系统目标协调，以及承接 Mission 的整体结果 |
| 系统产品团队 | 本域能力承诺、执行策略、状态机、控制闭环、保护与结果反馈 |
| 架构矩阵 COE | 共性契约与架构、跨团队边界、平台需求、参考方法和技术资产 |

矩阵参与能力定义，但不能仅根据 IDL 独立确定功能承诺；也不因为提供共用机制而代替 VCC 做场景决策。

## 6. 对早期建议的修正

当天较早的分析强调“业务牵引、平台交付”，并提出为工程成果明确交付责任。后续用户明确 COE 定位后，这一表述作如下收敛：

- 保留“技术成果应可使用、可验证、有人维护”。
- 软件组件的实现、发布和维护主体由相应业务或平台组织承接。
- COE 负责共同研究、技术共识、资产沉淀与应用反馈，不作为强交付中心。
- DO 与 TPM 的参与强度按议题需要确定，不默认成为全部技术工作的排期和交付负责人。

因此，早期的交付导向不能被当作当前组织定位。
