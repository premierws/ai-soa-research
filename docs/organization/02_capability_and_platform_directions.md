# 能力建设与平台提升方向

日期：2026-11-13。下列为建议方向，后续按业务需求选择范围；不代表已承诺同时建设全部平台组件。

## 1. 车辆能力模型与契约

将现有服务组织为具有业务含义的能力。每项能力应说明：能完成什么、对象与区域、输入类型、可用条件、硬约束、依赖和冲突、结果含义、车型及版本、责任主体。

形成能力描述、目标契约、结果契约和上下文语义的共用方法。系统产品确认含义与承诺，VCC 确认消费需求，矩阵组织双方收敛。

重点产出是规范、样例和方法。不能用一个 RPC 或一个字段的存在，直接证明某项完整能力已经具备。

## 2. 对外 Agent 与传统使用方交互

共同定义以下语义：

- 能力发现与当前可用性。
- 精确控制、相对控制、预定义场景、结构化目标组合。
- 请求来源、作用对象和授权范围。
- 接受、澄清、修改、取消、任务状态和结果。
- 上下文事实、估计和预测的来源、时间及可信度。
- 版本兼容和能力演进。

交互规范需由 VCC、消费方和系统执行方共同验证。MCP、A2A 或现有服务形式按需要选择，业务语义与传输协议分开。当前未决定必须采用某个协议。

## 3. 向内提升现有服务和接口

| 现状 | 建议处理 |
| --- | --- |
| 已有完整功能，输入结果清楚 | 复用并补能力描述和映射 |
| 已有功能但接口分散、过于底层 | 在系统产品侧形成稳定能力封装或目标适配 |
| 能执行但缺少结果关联或证据 | 补齐结果语义、必要关联及反馈 |
| 尚无对应功能或责任主体 | 明确真实能力缺口，转入相关产品建设讨论 |

矩阵沉淀能力—服务映射、缺口识别方法、接口演进模式和验证要求。既不要求全部服务重做，也不把外加工具调用包装视为功能完成。

soa_adaptor 保持通信和 IDL 桥接职责。目标理解、业务仲裁和 Mission 管理由相应业务负责。

## 4. 中间件与底软功能性能需求

| 业务问题 | 底座需求方向 |
| --- | --- |
| 当前状态是否可用于判断 | 区分读取结果、数据更新、源端时间与质量信息 |
| 是否能解释目标执行过程 | 必要的关联、状态与结果传递机制 |
| 并发和拥塞怎样处理 | 按语义确定队列、顺序、背压及错误反馈 |
| 跨核跨 ECU 是否稳定协作 | 启动、连接、重连、生命周期与隔离行为 |
| 如何定位失败 | 关联请求、状态、错误、版本和执行证据 |
| 功能性能是否满足业务 | 分别定义受理、起效、反馈、状态时效等预算 |

COE 帮助把业务问题转成可解释、可验收的底座需求。具体实现与交付归相应组织。不能将某个 Demo 的 10ms 周期直接变成所有能力的时延要求，也不统一强制所有接口配置可靠传输、队列或 E2E 门控。

## 5. 工程工具与公共机制

可围绕实际需求形成三类支撑：

1. 能力资产与追溯：能力到契约、服务、实例、车型配置和版本的映射，复用 service_arch 等基础。
2. 开发接入：契约与映射检查、适配模板、Mock、状态和结果模拟、参考样例。
3. 诊断：围绕 Mission 关联请求、子目标、系统反馈和失败原因，复用既有日志及诊断机制。

公共运行机制应通过真实复用需求识别。COE 组织研究和参考验证；形成产品化工具或组件时，需另有明确维护团队。领域策略不因复用机制而迁入公共平台。

## 6. 目标与契约验证

验证不仅包括连通、响应和性能，还需覆盖：契约理解、适用条件、硬约束、接受与完成的区分、冲突和抢占、手动操作、部分成功、失败、未知结果，以及版本差异。

COE 适合沉淀契约一致性方法、能力符合性检查、通用异常用例及环境需求。整车体验和功能验收由相应责任方承担。

## 7. 应用方式与评价

建议以真实业务切片检验方法，再提取可复用的机制。例如二排休息且不移动座椅、不改变前排设置，能够同时暴露目标表达、共享资源、任务协调和结果反馈问题。

评价维度可包括业务接入效率、契约和责任明确程度、方案复用情况、结果可解释性、变更可追溯性、底座限制是否可见。具体指标需按业务建立基线，不以服务数量、工具数量或会议次数作为主要价值证明。
