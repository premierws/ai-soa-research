# 调研脉络与判断依据

本文件按照讨论推进关系整理，并非逐字聊天记录。明确引用用户原话的部分使用引号，其余为研究归纳。

## 1. 从服务接口复用开始

起点：既有车控能力已通过 SOA 封装，希望将每个完整系统功能表现为 Agent 可以使用的能力。

第一层问题不是给服务增加一个可调用入口，而是服务的输入与输出是否足以支撑 Agent 正确使用。观察到已有接口既有动作请求，也有场景请求、状态订阅和部分目标型表达，适合逐项复用，而不适合统一机械包装。

判断依据：[代表性平台 IDL](../evidence/platform_idl/)、[既有请求字段调研](../references/soa_surveys/request_field_usage_survey.md)、[接口场景调研](../references/soa_surveys/interface_scenario_survey.md)。这些资料支持接口形态判断，不直接证明实车能力。

## 2. 将使用方从座舱扩展到多种入口

用户明确指出，座舱 Agent 只是一个消费者，还包括智能驾驶世界模型、手机等远程设备，以及未来可能的手机智能体。

由此形成的判断是：对外语义不应绑定自然语言或某个模型；精确请求和目标型请求均应被保留。一个传统界面也能调用场景，一个 Agent 也能下达精确请求。

## 3. VCC 规划强调端到端功能责任

VCC 规划材料包含从命令／场景、意图、任务、仲裁到跨域目标规划的链路，以及依赖系统能力实现端到端的方向。

规划正文中的“个人理解简述”进一步区分 Mission 管理、目标适配和 SOA 执行。它是研究参考，而非已经冻结的全部产品基线。

由此加强了一个判断：VCC 的价值需要通过完整任务与结果体现，不能停留在服务目录和调用中转。

## 4. 行业材料的启发与限制

用户提供的行业文章强调大量 SOA 能力被动态组合的可能性。启发在于场景可按需求生成、服务可被复用；不能据此推导模型应直接自由调度全部底层接口。

接口数量、最小颗粒度、并发调用和 OTA 都不能替代目标语义、控制边界与完成证据。材料中的具体产品事实未经独立核实。

## 5. 收敛为受约束的目标组合

用户明确认同：“开放受约束的目标组合能力，复用系统产品的执行能力，让 VCC 对其承接的 Mission 形成完整责任。”

这里确定了三项核心约束：外部表达目标，车辆能力有边界，VCC 承接任务责任；系统产品继续执行本域功能。

## 6. 从预定义场景走向动态场景

预定义场景可以通过编号和参数调用，但新组合无法逐个提前建立编号。由此讨论出稳定目标类型与可变目标集合的表达形式。

典型例子：二排右侧稍暖、灯光稍暗、不改变前排、尽量省电。需要预先定义热舒适和灯光能力、区域与约束含义，不必预先定义该组合的专用场景接口。

示例见 [目标请求](../examples/mission_request.json) 与 [示意 Proto](../examples/mission_contract.example.proto)。这些是解释性材料，不是可部署契约。

## 7. 场景沉淀成为业务闭环

用户提出：“如果用户请求命中了预定义场景，则直接按照预定义场景的业务流程执行。如果用户请求没有命中预定义场景，则由agent自行组合编排成为新的满足用户需求的扩展场景，而且将这个场景作为已知的用户场景记录下来，甚至通过伴生，将这些场景收集下来，作为agent后续版本规划中的预定义场景，不断扩展。”

进一步明确：命中须考虑约束和适用条件；候选场景、成功执行、个人已知场景与产品预定义场景是不同对象。失败记录也有价值，但不能被视为已验证能力。

## 8. 多 Agent 分工收敛

用户提出：“座舱agent更懂舱内用户需求，智能驾驶系统agent更懂车外态势，而车控agent是更懂车的存在。”

由此形成并被用户认可的建议是：车控相关跨系统场景、编排和目标仲裁更适合放在 VCC。用户对话、外界预测、域内控制和实时保护保持各自归属。

典型协作例子：孩子休息需求来自座舱，隧道预测来自智驾，车辆环境协调由 VCC 承接，具体通风策略仍由产品执行。

## 9. 结论强度

- 多 Agent 职责、目标组合、任务责任与场景演进，属于本次讨论形成的业务共识。
- IDL、底座说明、代码及旧调研，属于实现现状或接口事实的支持材料。
- 示例和协议比较帮助说明可行表达，不证明已有完整车控 Agent 已经实现。
- 统计来自原 SOA 样本，不可直接外推为全车企的软件比例或 Agent 无损转换率。
